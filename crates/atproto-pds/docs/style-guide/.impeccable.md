# impeccable — account portal

Design context for the `atproto-pds` account portal: the HTML pages under
`/account` that an account holder reaches with nothing but a browser.

Scope is the portal only. The OAuth consent screen (`src/oauth/consent.rs`),
the delegate sign-in page (`src/oauth/delegation.rs`) and the operator
dashboard (`src/admin/dashboard.rs`) carry their own stylesheets and are
deliberately not covered — consent in particular is a security surface whose
narrowness is a decision, not an oversight.

## Design Context

### Users

People running their own PDS. They hold the signing keys, read the logs, and
have a terminal open in the next window. `did:plc:iu5fzdrrfrc6kk7vmmatvin2`,
`at://…/app.bsky.feed.post/3msw44754okhn` and
`repo:app.bsky.feed.post?action=create` are information to them, not noise.

They arrive to do one specific thing — revoke a credential they no longer
recognise, move a handle, check who currently has access, read a record back —
and then leave. Nobody browses this. Most are the only account holder on the
server they operate, which means there is no support desk behind the interface:
if a page is unclear, the reader is the last line.

Some of what they do here is irreversible and frightening. Signing out
everywhere ends every session on every device. Changing a handle writes to a
public audit log that cannot be rewritten. Removing a delegate cuts off
somebody who may be mid-task.

### Brand Personality

**Sharp, dense, unimpressed.**

An operator's console, not a consumer settings screen. It does not persuade,
congratulate, or reassure. It states what is true, what a control will do, and
what it will not do, and then gets out of the way.

The voice already in the codebase is the target: exact, unhurried, willing to
name a limitation in the same breath as the feature. "Revoking one stops that
application renewing its access and leaves the others alone; a token it already
holds keeps working for up to 15 minutes." No adjective in that sentence is
doing promotional work, and the caveat is not buried.

Unimpressed is not unhelpful. The interface has no opinion about the user and
makes no attempt to be liked, but it is scrupulous about being understood.

### Aesthetic Direction

**Theme.** Honour `prefers-color-scheme`, and treat dark as a primary
composition rather than a set of overrides. Today the light palette is defined
in the base rules and dark is patched on top of it in a media query — which
makes dark structurally second-class, and it is the mode most of this audience
is actually in. Both should be designed, not one derived from the other.

**Density.** This is a scanning surface. Whitespace groups; it does not
comfort. A table of twelve grants should fit on one screen. Vertical rhythm
should be tight and consistent enough that a row boundary is obvious without a
rule under every row.

**Typography.** A distributed typeface, not the system stack — see the decision
record below. Three roles, and the third is functional rather than decorative:

- *Display* — page and section headings. May be a genuinely distinctive face;
  this is the one place with room for character.
- *Text* — prose, labels, table cells. A grotesque that holds up at 0.85–0.9em
  in dense tables, because that is where most of the words are.
- *Machine values* — DIDs, CIDs, AT-URIs, scope strings, record JSON. Monospace
  here is *semantic*: these are strings a person compares character by
  character, and a misread `0`/`O` or `1`/`l` is a real failure. Pick a face
  that disambiguates them explicitly.

**Colour.** Near-monochrome with one accent, and the accent is rare because
rarity is what makes it mean "this is the action". Three semantic tints beyond
that — affirmative, refusal, standing warning — and nothing else. Current
palette is 30-odd hand-picked hex values with no system behind them; it should
become a small token set in OKLCH, with neutrals tinted toward the accent hue.

**Anti-references.**

- *Terminal cosplay.* This brief — "sharp, dense, unimpressed", an operator's
  console, self-hosters — is exactly the one that produces monospace
  everywhere, phosphor green on black, ASCII box-drawing and a blinking cursor.
  It is costume. Monospace is for machine-readable values and nothing else.
- *Consumer settings screens.* Rounded cards, generous padding, an icon above
  every heading, reassuring illustrations, a success toast for changing an
  email address.
- *Marketing dashboards.* Hero metrics, sparklines as decoration, gradient
  accents, "at a glance" summaries of things that need to be read exactly.
- *Onboarding warmth.* Nobody is being welcomed. They are signed in already.

### Design Principles

1. **Say what a control does, including what it does not do.** The caveat goes
   next to the button, not in a help page. A person about to revoke something
   is owed the sentence about the 15-minute window.
2. **Raw values are content.** Show the DID, the CID, the full scope string.
   Do not summarise an identifier into something friendlier — for this
   audience that removes the information they came for.
3. **Density is a feature.** Prefer more on screen to more air around it.
   Whitespace earns its place by separating groups, not by softening the page.
4. **Dark and light are both first-class.** Neither is the "real" one.
5. **Nothing decorative that is not load-bearing.** Every rule, tint, badge and
   weight change must encode something. If it only looks designed, remove it.

## Technical constraints

Any design work here lives inside these. They are not negotiable without
changing the server.

- **Server-rendered HTML built from Rust format strings.** No build step, no
  framework, no component library, no preprocessor. The whole portal is
  `format!` calls in `src/http/portal.rs`, `portal_spaces.rs` and
  `repository.rs`.
- **One shared stylesheet**, inlined into every response by `page()` in
  `src/http/portal.rs`, covering all five sections. There is no cross-page CSS
  caching: the bytes ship on every page view. This is the strongest argument
  for a small token set and against elaborate CSS.
- **Content-Security-Policy** (`src/http/security_headers.rs`):
  `default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline';
  script-src 'unsafe-inline'; connect-src 'self'; form-action 'self';
  frame-ancestors 'none'; base-uri 'none'`. No external anything, ever.
- **Must work with JavaScript disabled.** The only script in the portal is the
  consent page's form-submit helper, which is outside this scope.
- **Accessibility.** Keyboard-reachable throughout, real `<label>` elements,
  and contrast that holds in both themes. Density must not be bought with
  low-contrast grey-on-grey.

## Decision record

### Typography: a distributed font, served from this origin

*Superseded an earlier "system fonts only" answer.*

Custom fonts are permitted. The CSP has no `font-src`, so it currently falls
back to `default-src 'none'` and **no font can load at all** — not even a
`data:` URI. Enabling this is a deliberate change, and there are two ways:

- `font-src data:` with the face inlined in the stylesheet. Self-contained, but
  the portal's CSS is inlined per response and therefore never cached, so the
  font bytes would ship on *every page view*. For a console meant to be fast,
  this is the worse option.
- **`font-src 'self'` and a same-origin asset route.** One cacheable request
  for the whole session. This is the recommendation: it is not new machinery,
  it mirrors `/account/repository/icon/{nsid}` in `src/http/icons.rs`, which
  already serves binary assets from this origin under `img-src 'self'`.

Two implementation notes for whoever builds it:

- The icon route requires a signed-in session. A font route **must not** — the
  sign-in page is served to unauthenticated visitors and needs the same
  typeface.
- Subset to Latin and the punctuation the portal actually uses, and ship WOFF2.
  Three faces unsubsetted would undo the reason for choosing `'self'`.

Faces are not chosen here. When they are, the constraint is a licence
permitting redistribution with a self-hosted server — SIL OFL or equivalent —
which rules out most commercial foundries.

### Scope: the portal only

The consent screen, delegate sign-in page and admin dashboard each carry their
own stylesheet. They are excluded on purpose: consent is a security surface
where narrowness and visual separation from the rest of the site are doing
work, and the admin dashboard has a different audience (the operator, not the
account holder). Extending this context to them is a separate decision.

## Status

A `/critique` pass and the fixes from it closed most of the gap between this
document and the stylesheet.

**Done.** Both themes are drawn as full token sets rather than light-plus-
overrides — the omission was not stylistic, it was a defect: `.muted` (the
most-used class here), `.sub`, the link colour and all three notice tints had
no dark value at all and were rendering at 3.2–3.8:1 against AA's 4.5. Every
token now clears AA on every surface it lands on. The type scale is five `rem`
steps replacing twelve accidental `em` sizes that compounded to 11px in table
cells. `:focus-visible`, `:hover`, `:active` and a reduced-motion guard exist
where previously there were none.

**Not started.** The distributed typeface. Still the system stack; it needs the
`font-src` decision recorded above and an asset route.

**Watch for.** `--accent` is tuned for a link on a page background and is *not*
a button fill — pairing them cost a 2.5:1 primary button in dark mode before it
was caught. `--btn-bg`/`--btn-text` and `--danger-bg`/`--danger-text` are
separate for that reason.

The style guide in this directory is hand-maintained and holds a copy of the
stylesheet rather than the stylesheet itself, so none of the above is tracked
automatically. Mirroring a change to `page()` into it is a manual step. See
`README.md`.
